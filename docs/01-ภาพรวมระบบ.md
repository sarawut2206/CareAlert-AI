# 1. ภาพรวมระบบและเหตุผลของการออกแบบ

## 1.1 ปัญหาที่ระบบนี้แก้จริง ๆ

ระบบดูแลช่วยเหลือนักเรียนของไทยมีโครงสร้างที่ดีอยู่แล้ว (รู้จักนักเรียนรายบุคคล → คัดกรอง →
ส่งเสริม/ป้องกัน → ช่วยเหลือ → ส่งต่อ) แต่จุดที่มักพังในทางปฏิบัติมี 4 จุด:

| จุดที่พัง | อาการที่เห็นจริงในโรงเรียน | สิ่งที่ระบบนี้ทำ |
|---|---|---|
| **นักเรียนไม่บอก** | เด็กที่ทุกข์ที่สุดมักเงียบที่สุด | ช่องทางไม่ระบุตัวตน + ช่องทาง "เป็นห่วงเพื่อน" |
| **บอกแล้วหาย** | ครูรับเรื่องแล้วงานล้น เรื่องค้าง | SLA มีกำหนดเวลา + เตือนเมื่อเกินกำหนด |
| **คัดกรองแล้วจบ** | ทำ SDQ ปีละครั้ง เก็บแฟ้ม ไม่มีใครติดตาม | บังคับ Follow-up ก่อนปิดเคส |
| **"ปกติ" ที่ไม่จริง** | ตอบแบบสอบถามผ่าน = ถูกตัดออกจากระบบ | สถานะ "ข้อมูลยังไม่เพียงพอ" ≠ "ปกติ" |

**ระบบนี้ไม่ได้พยายามเก่งกว่าครู** — พยายามทำให้ครูได้รู้เรื่องเร็วขึ้น
และทำให้เรื่องที่รู้แล้วไม่หายไประหว่างทาง

## 1.2 สิ่งที่ระบบนี้จงใจไม่ทำ

| ไม่ทำ | เหตุผล |
|---|---|
| วินิจฉัยโรค | การวินิจฉัยเด็กต้องใช้การสัมภาษณ์เชิงโครงสร้างโดยผู้ผ่านการฝึกอบรม |
| ทำนายว่าใครจะก่อเหตุ | ไม่มีหลักฐานว่าทำได้แม่นยำ และการทำโปรไฟล์สร้างความเสียหายต่อเด็ก |
| จับโกหก | เทคโนโลยีตรวจการโกหกไม่น่าเชื่อถือ และทำลายความไว้วางใจซึ่งเป็นหัวใจของระบบ |
| อ่านแชต/โซเชียล/กล้อง | เป็นการสอดส่อง ไม่มีหลักฐานว่าป้องกันเหตุได้ และผิดหลักคุ้มครองเด็ก |
| จัดอันดับ/ติดป้ายนักเรียน | ป้ายที่ติดตอนอายุ 14 อาจติดไปตลอดชีวิต |
| แจ้งตำรวจอัตโนมัติ | การตัดสินใจที่เปลี่ยนชีวิตเด็กต้องมีมนุษย์รับผิดชอบเสมอ |

### ทำไมเลือกแบบนี้

**ทำไมไม่ใช้ Machine Learning ตัดสินระดับ**

เพราะเมื่อผู้ปกครองถามว่า *"ทำไมลูกฉันถึงถูกเรียกไปคุย"* คำตอบต้องเป็นประโยคที่คนฟังเข้าใจ
ไม่ใช่ *"โมเดลให้คะแนน 0.83"* กฎที่เขียนไว้ล่วงหน้าทำให้:

- ตรวจสอบย้อนหลังได้ทุกเคส (บันทึก `rationale_json` ไว้ในทุกการประเมิน)
- แก้เกณฑ์ได้ทันทีเมื่อโรงเรียนพบว่าไม่เหมาะกับบริบท
- ไม่มีอคติแฝงจากข้อมูลฝึกที่ไม่มีใครตรวจได้
- เขียนเทสต์ครอบได้ทุกกฎ

**ทำไมใช้ SQLite แทน PostgreSQL**

โรงเรียนส่วนใหญ่ไม่มีทีมไอที การต้องดูแล database server เพิ่มอีกตัวมักทำให้ระบบตาย
ภายในหนึ่งภาคเรียน SQLite แบบไฟล์เดียวสำรองข้อมูลได้ด้วยการคัดลอกไฟล์
และรองรับนักเรียนหลักพันคนได้สบาย ถ้าโตกว่านั้นค่อยย้ายไป PostgreSQL

**ทำไม `node:sqlite` แทน `better-sqlite3`**

`better-sqlite3` ต้องคอมไพล์โค้ด native ซึ่งบนเครื่อง Windows ของโรงเรียนมักล้มเหลว
เพราะไม่มี build tools `node:sqlite` มากับ Node.js อยู่แล้ว → **ติดตั้งได้ทุกเครื่อง**

## 1.4 การไหลของข้อมูล (ตัวอย่างเคสจริง)

```
1. DETECT
   นักเรียนเปิดแอปตอนพักเที่ยง กด "เช็กอินสัปดาห์นี้"

2. DISCLOSE
   ตอบข้อ 6 ว่า "ถูกเพื่อนล้อ เกือบทุกวัน"
   → เซิร์ฟเวอร์ตอบกลับว่าให้เปิดชุดคำถามเรื่องการถูกรังแกเพิ่ม
   → นักเรียนเลือกได้ว่าจะตอบหรือข้าม

3. VALIDATE
   ตอบครบ 92% · เวลาต่อข้อ 4.2 วินาที · ไม่มีคำตอบขัดแย้ง
   → dataSufficiency = SUFFICIENT

4. ASSESS
   ความรุนแรง 2 · ความถี่ 3 · ระยะเวลา 2 · ผลกระทบ 3
   การขาดคนช่วย 3 · ความปลอดภัย 1 · แนวโน้ม 1
   → ดัชนีความห่วงใย 68/100

5. ALERT
   กฎที่ทำงาน:
     L3.BULLYING_ONGOING  ถูกรังแกต่อเนื่องและกระทบชีวิต
     L3.HIGH_INDEX        ดัชนี ≥ 65
     L2.SINGLE_DOMAIN     พบสัญญาณด้านการถูกรังแก
   ตัวปรับ:
     MOD.RETALIATION_RISK นักเรียนกลัวถูกเอาคืน
   → ระดับ 3 (ระดับสูงสุดที่ตรงเงื่อนไข)

   นักเรียนเห็น: "ขอบคุณที่ไว้ใจเล่าให้ฟัง ครูแนะแนวจะติดต่อเธอเร็ว ๆ นี้"
   นักเรียนไม่เห็น: ระดับ ดัชนี หรือชื่อกฎ

6. INTERVENE
   เปิดเคส → มอบหมายครูแนะแนวอัตโนมัติ
   ต้องรับเรื่องภายใน 4 ชั่วโมงเรียน · ต้องคุยกับนักเรียนภายใน 24 ชั่วโมงเรียน
   ระบบเตือนว่า "ต้องวางแผนคุ้มครองก่อนดำเนินการกับผู้กระทำ"

7. FOLLOW-UP
   ปิดเคสไม่ได้จนกว่าจะครบ:
     ☐ บันทึกว่าได้พูดคุยกับนักเรียนแล้ว
     ☐ ยืนยันความปลอดภัย
     ☐ มีบันทึกการดำเนินการหรือการส่งต่อ
   นัดติดตามอัตโนมัติที่ 3 / 7 / 30 วัน
```

## 1.5 บทบาทและสิทธิ์

| บทบาท | เห็นอะไร | ทำอะไรได้ |
|---|---|---|
| **นักเรียน** | เฉพาะของตัวเอง (ไม่เห็นระดับ/คะแนน) | เช็กอิน เล่าเรื่อง แจ้งเป็นห่วงเพื่อน ทำกิจกรรม |
| **ครูที่ปรึกษา** | เฉพาะห้องที่รับผิดชอบ | รับเรื่อง บันทึกการคุย ดำเนินการ ยกระดับ |
| **ครูแนะแนว** | ทั้งโรงเรียน | ทุกอย่างของครูที่ปรึกษา + ลดระดับ + ปิดเคสระดับ 4 |
| **ผู้ดูแลระบบ** | ทั้งโรงเรียน + ร่องรอยการใช้งาน | จัดการบัญชี นำเข้านักเรียน ตั้งค่า ลบข้อมูลตามนโยบาย |
| **ผู้บริหาร (ผอ.)** | **แดชบอร์ดข้อมูลรวมเท่านั้น — ไม่เห็นชื่อนักเรียน** | ติดตามว่าระบบตอบสนองทันเวลาไหม สั่งการเชิงนโยบาย |

**เหตุผลที่ผู้บริหารไม่เห็นรายเคส:** ผู้บริหารต้องตอบได้ว่า "ระบบดูแลทำงานทันเวลาหรือไม่"
ไม่ใช่ "เด็กคนไหนมีปัญหาอะไร" — ยิ่งคนเห็นข้อมูลอ่อนไหวน้อย นักเรียนยิ่งกล้าใช้ระบบ
และเมื่อจำเป็นจริง ผอ. สั่งการผ่านครูแนะแนวซึ่งเป็นผู้รับผิดชอบเคสได้เสมอ

**การเปิดดูข้อมูลนักเรียนทุกครั้งถูกบันทึกไว้** (`audit_log`) รวมถึงการเปิดดูที่ไม่ได้แก้ไขอะไร
เพราะการเข้าถึงข้อมูลอ่อนไหวของเด็กโดยไม่มีเหตุผลก็เป็นการละเมิดเช่นกัน

## 1.6 ฐานวิชาการที่ระบบอ้างอิง

| ระดับ | ฐานที่ใช้ | ใช้อย่างไรในระบบ |
|---|---|---|
| ระบบ | ระบบดูแลช่วยเหลือนักเรียน / MTSS | โครงสร้าง 2 ชั้น: ทุกคน + เฉพาะผู้ต้องการ |
| การเฝ้าระวัง | โครงสร้างเชิงมิติของ 9S / SDQ | ชุดคำถามหลัก 9 ข้อ (เขียนขึ้นใหม่) |
| อารมณ์เศร้า | โครงสร้างของ PHQ-A | ชุดคำถามเชิงลึกเรื่องอารมณ์ |
| การวินิจฉัย | T-DICA-R และการสัมภาษณ์โดยผู้เชี่ยวชาญ | **เหตุผลที่ระบบไม่วินิจฉัยเอง** — ส่งต่อมนุษย์เสมอ |
| การประเมิน/ส่งต่อ | แนวทาง WHO mhGAP / AAP GLAD-PC | Screen → Review → Refer → Follow-up |
| ป้องกันความรุนแรง | Behavioral Threat Assessment (NTAC) | ช่องทางรับแจ้ง + ทีมมนุษย์ + case management |
| ปัจจัยเสี่ยง/ปกป้อง | กรอบหลายระดับของ CDC | มิติ "ปัจจัยปกป้อง" และ "การมีคนช่วยเหลือ" |

**สิ่งที่ต้องพูดให้ถูก:** สิ่งที่ผ่านการตรวจสอบแล้วคือ *เครื่องมือและกรอบวิจัยเดิม*
ส่วน *ระบบนี้* ต้องผ่านการตรวจสอบแยกต่างหาก ดู [06-แผนการตรวจสอบ](06-แผนการตรวจสอบ.md)
