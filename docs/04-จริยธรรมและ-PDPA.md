# 4. จริยธรรม ความเป็นส่วนตัว และการคุ้มครองเด็ก

ระบบที่เก็บข้อมูลความทุกข์ของเด็กมีโอกาสทำร้ายเด็กได้พอ ๆ กับที่ช่วยเด็กได้
เอกสารนี้คือข้อผูกมัดที่ทั้งโค้ดและคนต้องปฏิบัติตาม

---

## 4.1 ความยินยอมและการบอกความจริงล่วงหน้า

นักเรียนต้องได้อ่านสิ่งเหล่านี้ **ก่อน** ใช้งาน (แก้ไขข้อความได้ที่หน้าผู้ดูแลระบบ):

1. ระบบนี้มีไว้เพื่อช่วยเหลือ ไม่ได้มีไว้จับผิดหรือลงโทษ
2. สิ่งที่เขียนจะถูกอ่านโดยครูที่รับผิดชอบระบบดูแลช่วยเหลือนักเรียนเท่านั้น **ไม่ใช่ครูทุกคน**
3. ระบบไม่ได้อ่านแชตส่วนตัว โซเชียลมีเดีย หรือกล้อง
4. ระบบไม่ได้วินิจฉัยว่าเป็นโรคอะไร และไม่ได้ตัดสินว่าเป็นคนแบบไหน
5. เลือกไม่บอกชื่อได้ และข้ามคำถามที่ยังไม่พร้อมตอบได้
6. **ข้อยกเว้นเรื่องความลับ:** ถ้ามีสัญญาณว่าตนเองหรือคนอื่นอาจไม่ปลอดภัย
   ครูจำเป็นต้องรู้ตัวตนเพื่อช่วยได้ทัน
7. ขอดูหรือขอลบข้อมูลของตัวเองได้ โดยติดต่อครูแนะแนว

> **ข้อ 6 คือข้อที่ห้ามซ่อน** ระบบแสดงข้อความนี้ซ้ำอีกครั้งบนหน้าจอก่อนเริ่มเล่าเรื่อง
> เมื่อนักเรียนเลือก "ไม่บอกชื่อ" และแสดงอีกครั้งทันทีที่ตัวตนถูกเปิดเผยจริง
>
> การทรยศความลับโดยไม่บอกก่อน จะทำให้ไม่มีนักเรียนคนไหนกล้าใช้ระบบนี้อีกเลย
> และข่าวจะกระจายเร็วกว่าที่ผู้ใหญ่คิดเสมอ

### สำหรับผู้ปกครอง

โรงเรียนควรแจ้งผู้ปกครองล่วงหน้าว่าระบบนี้คืออะไร ทำอะไร และไม่ทำอะไร
พร้อมช่องทางสอบถาม ตาราง `consents` รองรับทั้งความยินยอมจากนักเรียนและผู้ปกครอง

---

## 4.2 การเก็บข้อมูลเท่าที่จำเป็น (Data Minimization)

| เก็บ | **ไม่เก็บ** |
|---|---|
| คำตอบแบบเช็กอินและข้อความที่นักเรียนเขียนเอง | ข้อความจากแชตส่วนตัวหรือโซเชียลมีเดีย |
| เวลาที่ใช้ตอบต่อข้อ (ใช้ตรวจคุณภาพข้อมูล) | ตำแหน่งที่ตั้ง (location) |
| ห้องเรียนและผู้ปกครองที่ติดต่อได้ | ภาพถ่าย เสียง วิดีโอ |
| บันทึกการดำเนินการของบุคลากร | ข้อมูลชีวมิติหรือการวิเคราะห์ใบหน้า |
| ร่องรอยการเข้าถึงข้อมูล | ประวัติการใช้เว็บของนักเรียน |

**ข้อความสะท้อนตัวเองในกิจกรรมทักษะชีวิต** จะไม่ถูกส่งให้ครูอ่าน
เว้นแต่พบสัญญาณความปลอดภัย — และหน้าจอบอกนักเรียนตรง ๆ ว่าเป็นแบบนี้

---

## 4.3 ใครเห็นอะไรได้บ้าง

| บทบาท | ขอบเขต |
|---|---|
| ครูที่ปรึกษา | **เฉพาะห้องที่ตนเป็นที่ปรึกษา** หรือเคสที่ถูกมอบหมายให้ |
| ครูแนะแนว | ทั้งโรงเรียน (เป็นผู้รับผิดชอบระบบดูแลช่วยเหลือ) |
| ผู้ดูแลระบบ | ทั้งโรงเรียน + ร่องรอยการใช้งาน |
| ผู้บริหาร | ควรใช้บัญชีตามบทบาทจริง **ไม่ควรมีบัญชีที่เห็นทุกอย่างโดยไม่มีเหตุผล** |

**การเข้าถึงทุกครั้งถูกบันทึก** รวมถึงการเปิดดูที่ไม่ได้แก้ไขอะไร
(`case.view`, `student.view`, `students.search`)

โรงเรียนควร**สุ่มตรวจ audit log อย่างน้อยภาคเรียนละครั้ง** — ดูว่ามีการเปิดดูข้อมูล
นักเรียนที่ไม่เกี่ยวข้องกับหน้าที่หรือไม่ นี่เป็นการควบคุมที่สำคัญกว่าการตั้งรหัสผ่านให้ยาก

---

## 4.4 การแจ้งเตือนออกนอกระบบ

Webhook แจ้งเตือนส่งเฉพาะ **หมายเลขเคสและระดับ** เท่านั้น

```
[CareAlert] เคสระดับ 4 — ต้องตรวจสอบความปลอดภัยทันที (เคส #12)
กรุณาเข้าระบบเพื่อดูรายละเอียด
```

**ไม่ส่ง** ชื่อนักเรียน ห้องเรียน หรือข้อความที่นักเรียนเขียน
เพราะแชตกลุ่มไม่ใช่ที่ปลอดภัยสำหรับข้อมูลอ่อนไหวของเด็ก —
ข้อความถูกแคปหน้าจอ ส่งต่อ และค้นย้อนหลังได้โดยที่โรงเรียนควบคุมไม่ได้

---

## 4.5 ระยะเวลาเก็บข้อมูล

ค่าเริ่มต้น (ปรับได้ใน `server/.env`):

| ประเภท | ระยะเวลา | ตัวแปร |
|---|---|---|
| บันทึกการเช็กอิน | 1 ปี | `RETENTION_CHECKIN_DAYS` |
| เคสที่ปิดแล้ว | 3 ปี | `RETENTION_CASE_DAYS` |
| ร่องรอยการใช้งาน | 3 ปี | `RETENTION_AUDIT_DAYS` |

การลบต้องกดโดยผู้ดูแลระบบ (มีโหมดตรวจสอบก่อนลบ) — **ไม่ลบอัตโนมัติ**
เพื่อให้มีคนรับผิดชอบการตัดสินใจเสมอ

> โรงเรียนควรตกลงระยะเวลาร่วมกับฝ่ายกฎหมาย/ต้นสังกัด และ**สำรองไฟล์
> `server/data/carealert.db` ก่อนลบทุกครั้ง**

---

## 4.6 สิทธิ์ของเจ้าของข้อมูล (PDPA)

| สิทธิ์ | ทำอย่างไรในระบบ |
|---|---|
| ขอดูข้อมูลของตัวเอง | นักเรียนดูประวัติเช็กอินได้เอง · ขอส่วนที่เหลือผ่านครูแนะแนว |
| ขอแก้ไข | ติดต่อครูแนะแนว (ระบบบันทึกการแก้ไขไว้เสมอ) |
| ขอลบ | ครูแนะแนว/ผู้ดูแลพิจารณาร่วมกัน — **ยกเว้นข้อมูลที่จำเป็นต่อการคุ้มครองเด็กตามกฎหมาย** |
| ถอนความยินยอม | บันทึกที่ `consents.withdrawn_at` |

**สิ่งที่ต้องระวัง:** สิทธิ์ในการลบไม่ครอบคลุมกรณีที่การลบจะทำให้เด็กเสี่ยงอันตราย
หรือขัดกับหน้าที่คุ้มครองเด็กตามกฎหมาย ต้องพิจารณาเป็นรายกรณีและบันทึกเหตุผลไว้

---

## 4.7 มาตรการทางเทคนิค

| มาตรการ | สถานะในโค้ด |
|---|---|
| รหัสผ่าน hash ด้วย scrypt + salt | ✅ `lib/crypto.js` |
| ล็อกบัญชีชั่วคราวเมื่อกรอกผิด 8 ครั้ง | ✅ `routes/auth.js` |
| บังคับเปลี่ยนรหัสผ่านชั่วคราวก่อนใช้งาน | ✅ |
| JWT หมดอายุ 8 ชั่วโมง | ✅ ปรับได้ที่ `JWT_TTL` |
| จำกัดอัตราการเรียก API | ✅ `middleware/ratelimit.js` |
| ตรวจสิทธิ์ทุกเส้นทาง (ไม่พึ่งการซ่อนปุ่ม) | ✅ `middleware/auth.js` |
| ส่วนหัวความปลอดภัย (nosniff, DENY frame) | ✅ `index.js` |
| audit log ครอบคลุมการอ่าน | ✅ `lib/audit.js` |

**สิ่งที่โรงเรียนต้องทำเพิ่ม (ระบบทำแทนไม่ได้):**

- ตั้ง `JWT_SECRET` ของตัวเองใน `server/.env`
- ใช้ HTTPS เสมอเมื่อเปิดให้เข้าถึงจากภายนอก
- สำรองไฟล์ฐานข้อมูลเป็นประจำ และเก็บสำเนาไว้คนละที่
- **จำกัดการเข้าถึงเครื่องที่ติดตั้งระบบ** — ไฟล์ฐานข้อมูลคือข้อมูลทั้งหมด

## 4.8 ความเสี่ยงที่ต้องยอมรับและวิธีลด

| ความเสี่ยง | วิธีลดในระบบนี้ | สิ่งที่ยังเหลืออยู่ |
|---|---|---|
| **เตือนเกิน** (false positive) | ยอมรับโดยตั้งใจ | ครูเสียเวลาคุยกับนักเรียนที่ไม่ได้มีปัญหา |
| **พลาด** (false negative) | เกณฑ์ความปลอดภัยต่ำที่สุด + ทุกช่องทางมีมนุษย์ดู | ยังพลาดได้ — ระบบไม่ใช่ตาข่ายที่ไม่มีรู |
| **ตีตราเด็ก** | ไม่แสดงระดับให้นักเรียน · ไม่จัดอันดับ · ใช้คำว่า "ระดับการดำเนินการ" | ครูอาจพูดถึงเด็กในทางที่ตีตราอยู่ดี → ต้องอบรม |
| **เด็กเลิกใช้เพราะกลัวถูกเปิดเผย** | บอกข้อยกเว้นล่วงหน้าเสมอ + ช่องทางไม่ระบุตัวตน | ถ้าโรงเรียนใช้ผิดครั้งเดียว ความไว้วางใจหายทั้งรุ่น |
| **ข้อมูลรั่ว** | audit log · จำกัดสิทธิ์ตามห้อง · ไม่ส่งข้อมูลอ่อนไหวออกนอกระบบ | เครื่องที่ติดตั้งถูกเข้าถึงทางกายภาพได้ |
| **ครูพึ่งระบบมากเกินไป** | แสดงเหตุผลทุกครั้ง · ย้ำว่าเป็นการตัดสินใจของครู | ต้องอบรมและย้ำในทางปฏิบัติ |

---

## 4.9 ข้อห้ามในการนำระบบไปใช้

**ห้ามใช้ระบบนี้เพื่อ:**

- ประเมินหรือให้คุณให้โทษกับครู จากจำนวนเคสในห้องที่รับผิดชอบ
  (จะทำให้ครูเลี่ยงการบันทึกเคส ซึ่งอันตรายกว่าไม่มีระบบเลย)
- จัดอันดับห้องเรียนหรือโรงเรียน
- ประกอบการพิจารณาโทษทางวินัยของนักเรียน
- คัดเลือกนักเรียนเข้าโครงการ หรือกีดกันออกจากกิจกรรม
- ส่งข้อมูลรายบุคคลให้หน่วยงานภายนอกโดยไม่มีฐานทางกฎหมายและไม่บอกนักเรียน

หน้าภาพรวมจึงกลบข้อมูลกลุ่มที่มีจำนวนน้อยกว่า 5 คน และมีข้อความกำกับไว้ทุกครั้ง
